# XScope engineering constraints

- All platform services are Rust. Use kube-rs for Kubernetes CRD types, cluster-agent and Operator; retain their process/RBAC boundaries. Keep every Rust package under rust/crates with the workspace manifest at rust/Cargo.toml. Use SeaORM for business database access.
- Build, test, generate and package applications through Bazel targets only. Do not run `cargo build/test`, `go build/test`, `uv run`, `pip install` or `npm run` as an alternative build path. Language manifests remain dependency/IDE inputs; Bazel repository rules may resolve them.
- Implement backend stages in this order: SSE/cancellation; InferencePool and llm-d EPP; RoutePolicy and revision pools; Operator autoscaling/PDB/pools and ownership; billing reservations/idempotent HTTP usage delivery/events; multicluster desired state/heartbeat/ACK; telemetry/SLO/audit; payment/tax/inference API expansion.
- Gateway usage delivery is HTTP with a bounded volatile queue, not a local WAL/SQLite/archive mode. Do not reintroduce the retired implementation. Preserve historical PVC/object evidence; only the read-only one-time cutover guard may inspect legacy logs.
- Do not expand UI ahead of the backend contracts. Verify behavior before advertising it as implemented.
- Preserve unrelated workspace changes and unrelated Kubernetes resources. Local development data resets are limited to XScope business data and its quota/event state, not Keycloak identities or other applications.

## Credential and publication safety

- This repository is intended for public GitHub publication. Never write real access keys, passwords, API tokens, session cookies, private keys, signed URLs, account IDs, private bucket/access-point names, aliases or deployment endpoints into repository files, including this document, examples, tests, generated reports and commit messages. Use unmistakably synthetic fixtures/placeholders. Encoding a secret is not redaction.
- Put actual deployment configuration AND credentials in Kubernetes Secrets (or an approved external secret manager). Send secret manifests through stdin, with captured/suppressed output; do not use plaintext command arguments, shell history, shell tracing, client-side apply annotations, ConfigMaps or committed env files. Do not print Secret data, environment dumps or raw cloud error bodies. Inspect only metadata, bounded error codes and redacted status.
- Temporary private configuration, credentials, cloud responses and sensitive backups must live OUTSIDE the repository and its worktrees, in dedicated 0700 directories with 0600 files. Git ignore rules are defense-in-depth, not permission to store credentials in the workspace. Keep secrets out of Bazel inputs, action env, cache keys and build logs; inject only into the runtime child after builds finish.
- Do not copy user-provided credentials from chat into documentation. Recommend rotation when credentials were disclosed in chat or logs; never rotate/revoke credentials, widen IAM/AP/Bucket policies, disable public-access protections or set irreversible retention policies without explicit authorization.
- Before publication, run the repository secret scan against the working tree and Git history, with redacted output. A clean scan is not proof that no secret exists. Fix any confirmed tracked exposure and rotate affected credentials; do not rewrite Git history or force-push without explicit authorization. Do not push while known exposures remain.
