# 计费容量：1 万客户 / 每天千亿 token

结论：客户数不直接决定压力，token 也不是逐个写数据库；请求率、账户热点、事件倍数、历史保留与磁盘持久化才决定容量。本轮优化减少消费游标的写放大和锁竞争，**当前本地低资源部署仍未通过每天千亿 token 的生产容量验收**。

## 把业务量换成系统量

100,000,000,000 token / 天约为 1,157,407 token / 秒。以下是均匀流量的数学换算，不是压测结论，平均 token 数应包括实际计费的输入和输出：

| 平均 token / 请求 | 请求 / 天 | 平均请求 / 秒 | 正常完成请求的 Outbox 事件 / 天 |
| --- | ---: | ---: | ---: |
| 1,000 | 100,000,000 | 1,157.4 | 400,000,000 |
| 5,000 | 20,000,000 | 231.5 | 80,000,000 |
| 10,000 | 10,000,000 | 115.7 | 40,000,000 |

当前一次非零费用成功请求通常产生 1 条预占、1 条用量、1 笔交易/2 条分录和 4 条事件（created、dispatched、ledger.posted、settled），以及 Gateway 同步 reserve/dispatch HTTP 和异步最终用量 HTTP 上报；重试、失败、退款会改变这个比例。每个 token 和每个 SSE chunk 不单独写财务事件。

以 5,000 token 为例，若假设峰值为均值 5 倍，峰值约 1,157 请求/秒。1 万客户并不保证均匀分摊，单一大客户的串行资金锁仍可能成为热点。8,000 万事件/天即使仅按平均每条 1 KiB 粗估，也约 76 GiB/天 payload，尚未计索引、数据库 WAL、复制和备份。正式容量规划必须测实际平均行大小与保留期，而不是依赖这个示例。

## 已实现的优化

- 空轮询、没有新投递进度的重放、重复 ACK 不更新消费者元组，也不执行 `SELECT FOR UPDATE`。
- 消费进度仅锁账户下的 consumer 行，不与正常资金预占/结算争抢账户锁；首次注册仍有插入/外键成本。生产事件序号继续在资金事务内串行分配，保证提交顺序。
- 上一批 ACK 可携带在下一次 poll 内，最多一次游标更新；旧接口保持兼容。
- 返回 `has_more` / `retry_after_ms`，供调用方批量追赶及空闲退避。未实现常驻生产消费者或全租户调度器。
- 余额、冻结和 Key 月费用已改为事务内增量汇总；缺失时账户锁内回填，初始化后的预占不再做历史 SUM。Gateway 快照批量读取汇总，生成下一事件序号只读取 sequence。见 [汇总一致性与切换限制](billing-projections.md)。
- 未决预占使用有索引的 keyset 分页而非 OFFSET，只读发现，不自动解冻。

PostgreSQL 的行级排他锁本身也可能引起磁盘写入，因此无变化路径连排他锁一起避免，而不只是省略 UPDATE。[PostgreSQL 行锁说明](https://www.postgresql.org/docs/16/explicit-locking.html#LOCKING-ROWS)

UPDATE 生成的旧元组需要 VACUUM 回收；减少无意义更新可以降低这部分维护工作，但不替代 autovacuum 配置和监控。[PostgreSQL Vacuum 说明](https://www.postgresql.org/docs/16/routine-vacuuming.html)

### 消费游标写入量示例

假设每天 8,000 万事件、每批 100 条始终满批、两个独立消费者：分开 poll/ACK 约 320 万次进度更新/天；合并后约 160 万次/天（平均约 18.5 次/秒，忽略首次/末批）。实际小批量/低延迟拉取会增加更新次数，因此这不是上限。

空闲写入变成零不代表空闲成本为零：1 万账户每秒轮询一次仍有 1 万 HTTP 请求/秒，以及事务和账户/游标/事件查询。调用方应采用退避、抖动、有限并发，并在后续生产事件分发阶段采用活跃账户调度/分片消费；本轮没有伪造已经接入 Kafka/NATS 的能力。

## 隔离验证（2026-09-05）

通过 `bazel run //tools:billing_protocol_smoke` 启动两个真实控制面、两个 Gateway、独立 PostgreSQL。数据库容器限制 0.5 CPU / 192 MiB；控制面在宿主机运行。测试先验证资金竞争、故障回滚和真实行锁隔离，再装入 10,000 个测试账户、100,000 条事件和 10,000 个已追平游标。

首次成功探测：8 并发、1,000 次均匀抽样空轮询，约 1,279.2 请求/秒，P50 6.1ms、P95 8.1ms；消费者元组版本/更新时间均未变化。容器和测试数据已清理，未向本地集群写入这些样本。

同机并行进行 Linux release 编译时再次探测，约 728.7 请求/秒，P50 8.9ms、P95 23.0ms，仍为零游标更新。资源竞争导致结果明显变化，也说明这些短测数字不能当作容量承诺。

这是不足一秒的热缓存空页探测，不含持续推理、海量历史、持久消费副作用、长稳态 VACUUM、故障切换、单账户热点，也未模拟真实 GPU。因此它只验证规模下的查询行为，不证明千亿 token 吞吐、更不是“优化了多少倍”的前后对比。

## 下一批必须处理的瓶颈

1. **投影冷启动与运维**：事务内余额/冻结/月费用汇总、回填和显式一致性检查/重建已实现。首次回填仍随历史量增长且占用账户锁；大规模上线需预热与维护窗口，不能混跑旧非投影写入者。后续归档需要可靠期初基线，不能直接删源记录后重建。
2. **Gateway HTTP 并发**：准入由单工作线程处理，上报默认四个 worker，1024 个共享槽位覆盖在途与未确认请求。HTTP RTT、资金行锁和队列容量会限制吞吐；需要实测有界并发、拒绝率和 Pod 丢失的待核查规模，不把删除 fsync 等同于生产认证。
3. **历史保留**：Gateway 本地 WAL/归档代码已移除，见 [HTTP 投递边界](usage-delivery.md)。PostgreSQL Outbox/用量/账本仍需按留存要求制定分区归档、备份和消费者最小 ACK 边界，不能直接删除尚未消费的事件；历史对象证据与 PVC 不随代码清理删除。
4. **生产消费分发与热点**：租约消费者、退避、幂等副作用与延迟监控已接入；长期积压、分片策略及吞吐仍需压测。资金热账户串行化需测量后再拆分授权额度，不为并发绕开预算约束。
5. **持续验收**：用实际请求大小与热点分布测均值/峰值；观测端到端准入 P95/P99、账户锁等待、数据库 I/O、HTTP 队列年龄、消费者 lag、积压恢复耗时和未知用量率。故障恢复后必须核对中央冻结、缺失用量、幂等扣费和预算约束，再决定数据库/磁盘/副本配置。

证据提交、双人审批、损失豁免和生产消费者已有后端契约；供应商自动取证、正式支付/税务联调以及完整多集群生产容量仍需验证。
